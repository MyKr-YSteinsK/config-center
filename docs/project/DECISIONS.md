# 长期决定

下列标识沿用 2026 年接管前的决定记录。实现细节以当前代码、测试和可运行配置为依据。

| 标识 | 决定与理由 |
| --- | --- |
| A | 基线采用本地、单实例架构。进程内 Watch、限流和首行协调便于演示和验证。出现真实多实例需求时单独评估。 |
| B | 先保证事务与数据完整、协议一致及可复现验证，再扩展功能。关键实现应能在面试中解释取舍。 |
| C | MySQL schema 由 Flyway 管理。V1 至 V3 已应用，后续仅追加新迁移，以便兼顾已有数据库和空库安装。 |
| D | H2 保持低成本本地与测试入口。MySQL 特有的 schema、锁、排序和重启行为使用独立 MySQL 证据。 |
| E | 配置和 Feature Flag 历史追加写入。回滚从旧快照生成新版本，保留操作轨迹。 |
| F | 配置 Watch 使用持久的 `app + env` 修订号。多 key 可以独立增长业务版本，因此 revision 与写入同事务推进，并在提交后通知。 |
| G | 当前采用长轮询。以全局/命名空间容量、超时和完成清理控制等待资源。 |
| H | 将磁盘缓存视为外部输入。校验响应结构以后才允许 ETag、304 和瞬时失败回退。 |
| I | 历史用版本游标做有界倒序分页，限制数据库读取和响应成本。 |
| J | 正式交接正文优先用获授权的 Issue 或私有渠道。长期成果进入代码、文档和 Git，临时 Plan 与 patch log 保持在执行入口。 |
| K / D-009 | 历史上的远端人工发布规则已由 D-011 接续。原始说明保存于 [接管前决定记录](https://github.com/MyKr-YSteinsK/config-center/blob/0258b9cef02ea74a40989d035c79256c776409c0/docs/project/DECISIONS.md)。 |
| L | 以实际仓库和运行证据确定实施状态。旧快照用来追溯来源，发生冲突时在当前状态记录差异。 |
| D-011 | `Config-Plan02` 中的用户决定。正常任务在必要验收和边界检查后，快进推送已配置上游并实际比对远端 SHA。分支创建、强推、改历史、标签、版本、部署和破坏性操作各自需要相应授权。 |

## Config-Plan03 · 2026-11-24

用户选定先推进单仓 Java 后端维护。首轮纠正 CLI 传输、回滚原因存储和条件读取。下一轮先处理 CLI 与 Watch 故障恢复，依次再做写入竞争与一致性、按调用链重构与诊断、可复演展示。各轮实施范围单独确定。跨仓库、前端、SDK 及发行仍是候选。[Issue #2](https://github.com/MyKr-YSteinsK/config-center/issues/2)

两类回滚的请求上限维持 500 个 UTF-16 代码单元，历史保留原有 `rollback-to=<目标版本>` 前缀。19 位正版本、分隔符和满长原因合计最长 533。V3 只将两列扩为 `VARCHAR(600) NULL`，给既有历史和旧调用方保留原表示，也允许继续使用当前 Flyway 历史与唯一约束。
