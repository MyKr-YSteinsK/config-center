## Config-Plan03 · 2026-11-24

用户选定先推进单仓 Java 后端维护。首轮纠正 CLI 传输、回滚原因存储和条件读取。后续顺序定为 CLI 与 Watch 故障恢复、写入竞争与一致性、按调用链重构与诊断、可复演展示。各轮实施范围单独确定。跨仓库、前端、SDK 及发行仍是候选。[Issue #2](https://github.com/MyKr-YSteinsK/config-center/issues/2)

两类回滚的请求上限维持 500 个 UTF-16 代码单元，历史保留原有 `rollback-to=<目标版本>` 前缀。19 位正版本、分隔符和满长原因合计最长 533。V3 只将两列扩为 `VARCHAR(600) NULL`，给既有历史和旧调用方保留原表示，也允许继续使用当前 Flyway 历史与唯一约束。

## Config-Plan04

CLI 从游标 0 订阅。首个有效 Watch 观察、变化通知和较小 revision 均须再读列表才确认。确认表达列表读取覆盖的观察下界，最多推进到该读取之前观察的 revision。有效 200 与本次具体 ETag 对应的有效 304 都是读取证据。瞬时失败回退的旧缓存可展示，恢复期间保留原确认进度。观察到较小 revision 并成功读取后，采用该较小值重新订阅。

恢复以一轮所需的 Watch 观察和配置确认为单位。默认 30 秒内按至少 1 秒的间隔调度恢复尝试。配置读取待确认时直接补取，只有观察缺失时再 Watch。两种传输仍有独立断路器，已开始的内部尝试按原超时收尾。失败预算耗尽、终止错误或线程取消结束会话。对所有者先讲具体体验和证据，详细约定在 [开发入口](../../AGENTS.md)。[Issue #3](https://github.com/MyKr-YSteinsK/config-center/issues/3)

## Config-Plan05 · 2026-11-25

MySQL 同版本和首次创建继续使用当前事务与唯一约束。复现的两种等值拼写在首条 revision 上竞争时，InnoDB 选择回滚一笔，应用将 `CannotAcquireLockException` 映射为现有 409/4091。成功方的当前行、历史与 revision 同一事务提交，通知在提交后发送。读回后是否提交新的操作由调用方决定。[Issue #4](https://github.com/MyKr-YSteinsK/config-center/issues/4)

保存断连后用独立读回核对效果。历史可显示曾经保存的值，现有 trace、operator 和 reason 各有用途，历史缺少唯一的持久请求身份。是否引入回执、幂等键及新的写入前置条件，按实际使用需求另行决定。

## Config-Plan06 · 2026-11-25

用户选定精确名称。H2 和 MySQL 的配置、旗标、revision、写授权与 Watch 统一按原字符串匹配，包括前后空格、大小写和 Unicode 表示。MySQL V4 使用 `utf8mb4_0900_bin`。保留现有灰度算法与存量当前旗标名，原精确名称的分桶保持。[Issue #5](https://github.com/MyKr-YSteinsK/config-center/issues/5)

两类旧历史保留原始拼写和完整内容，使用当前行主键确定查询和回滚归属。当前与 revision 的 scope 有歧义时，由所有者按最新预检指纹选择一个已观察且有对应授权的目标。配置的写授权保持精确范围。升级停旧写入并用可恢复的 V3 备份保护数据，新 CLI 从独立缓存代际获取有效 200。细节与恢复步骤见 [精确名称与 V4 迁移](IDENTITY_MIGRATION.md)。

## Config-Plan07 · 2026-11-25

用户选定四类写入可选编号。每次请求按当前精确 scope 授权。同 scope 的编号跨四类操作共享，SQL 唯一约束决定并发归属，意图 v1 用精确代码单元和带类型字段做 SHA-256。应用先占位，然后跟业务效果一同提交成功回执。重放只读原结果，当前值继续用原 GET。失败释放占位，竞争后用新事务读回，Watch 以提交为界。[Issue #6](https://github.com/MyKr-YSteinsK/config-center/issues/6)

V5 只添回执表，延续现有权限、CLI 和无编号写入。回执持续保留并进入业务的一致性备份。旧版本会忽略编号，切换先停旧写入者。保留带版本的摘要和结果格式，回执损坏时停止重放。[写入回执合同](WRITE_RECEIPTS.md)

## 交接与恢复

Config-Plan10 采用工程孵化器 `f50e2b1682af21842a730f20c8533cbc3372a72f` 的交接规则。J、L 和 D-011 沿用。根入口恢复仓库目标和当前状态，GPT Project Main 审查路线及其保留事项，Codex Native 可直接接收用户任务。多个来源需要统筹时，按需使用一个 Codex 对话协调。 [Issue #9](https://github.com/MyKr-YSteinsK/config-center/issues/9) · [同步入口](../项目源文件/00-START_HERE.md)

- 正式交接正文留在获授权的目标 Issue 或私有渠道。公共 Issue 只放可公开的内容。Issue 不可读时，以用户提供的完整正文或获授权的可读私有文件核对适用版本、边界与验收。仍缺必要依据时，仅暂停依赖它的动作。仓库外副本按既有约定或用户指定保存。
- 共享核验执行一次。回执把相同提交、构建与环境上的结果分别关联到各任务的验收，记录各自仍缺的证据。依赖、写入或资源有冲突时处理受影响的部分，独立且已获授权的工作可继续。
- 方向未定、证据冲突或选择代价高时，先核对目标与硬约束，比较不同候选，并选能区分它们的最小验证。提前说明继续、换路或停止的条件。重大范围、数据或发布决定由所有者作出，明确边界内的工作直接推进。提交、推送、合并、部署与发布各自按实际授权判断。
