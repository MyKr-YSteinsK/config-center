# 项目目标

`config-center` 展示一个 Java 后端如何安全地写入配置、管理版本、解释灰度结果，以及在并发、回滚和网络失败时维持明确的行为。简历与面试以可重复运行的代码、测试和故障演示作为证据。

## 现行范围

- 一个 Spring Boot 服务端和一个 Java CLI 演示客户端。Java 17、Spring Boot 3、Maven 多模块、主机 loopback 默认值。
- 本地与自动化快测用 H2，持久化用 MySQL + Flyway。Compose 提供可重建的本地环境。
- 配置按精确 `app + env + key` 管理，Feature Flag 按精确 `app + env + name` 管理。写权限及配置 Watch 使用同一精确 scope。服务提供版本历史、回滚、条件读取、配置 Watch、灰度决策和诊断指标。

## 需要保住的行为

- 两类历史均追加写入，由精确当前对象持有，保留历史原始拼写。回滚使用目标快照产生新业务版本。已有 API 路径、JSON 字段、主要 HTTP 状态及错误码继续兼容。
- 配置变更事务同时写入当前值、历史和 `app + env` 的 namespace revision。Watch 使用 namespace revision 并在提交后通知，业务版本和 JPA 乐观锁版本各司其职。
- 四类写入可带编号，成功回执与业务变化同事务。按本次精确写权限重放旧结果，编号缺省沿用旧语义。回执与业务历史使用一致性备份。[写入回执](WRITE_RECEIPTS.md)
- 历史分页有上限。配置列表和弱 ETag 由同一份有序快照生成。客户端只有验证缓存响应结构后才使用 ETag、304 或瞬时失败回退。
- MySQL 持久 schema 由追加式 Flyway 迁移管理。V4 对存量名称先按旧规则预检，歧义由所有者审查，恢复使用匹配的 V3 备份。真实凭证、私有配置和本地主库数据单独保管。[V4 迁移合同](IDENTITY_MIGRATION.md)
- 调整接口或交互以前先验证原有行为，再用场景与测试证明改造收益。涉及 MySQL 或并发行为空间时采用对应环境的证据。

## 阶段与成功标准

当前阶段为单仓后端迭代。Config-Plan03 已修复 CLI 查询传输、历史原因长度和条件读取。Config-Plan04 使 CLI 在 Watch 收到通知后按实际读取确认进度，并可在有限时间内从刷新失败恢复。使用 [运行手册](RUNBOOK.md) 从干净检出恢复，执行两个模块的验证，并能在本机演示写入、读取、灰度、回滚与客户端行为。 [当前状态](CURRENT_STATE.md) 记录实际运行证据。

Config-Plan05 已验证真实 MySQL 写入竞争、409 锁冲突和断连读回。Config-Plan06 在隔离 MySQL 中验证了名称分离、旧历史、备份恢复，以及真实 CLI 的新缓存切换。Config-Plan07 做到了响应丢失后跨进程取回回执。Config-Plan08 收拢四条写入链，在相同数据上对照新旧 HTTP 和数据库，并在原 V5 库重放四类旧回执。后续优先评估维护收益、低基数诊断和固定数据集性能基线。前端、SDK、跨项目联动、发布流程、权限体系和分布式能力由用户按 [升级提案](../项目源文件/UPGRADE_ROADMAP.md) 选择。

长期理由见 [决定记录](DECISIONS.md)，具体行为见 [架构地图](../project-map.md)。
