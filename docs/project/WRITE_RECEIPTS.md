# 写入编号与持久化回执

保存后回信丢失时，调用方可以用同一个编号和原内容再发一次。服务端如果已经保存成功，会返回当时的结果。一次新的保存使用新的编号。

## 调用合同

四个现有 POST 路径支持可选的 `Idempotency-Key`。它们是 `/api/configs`、`/api/configs/rollback`、`/api/features`、`/api/features/rollback`。编号由调用方发出请求以前生成并保留。项目接受 1–128 个 ASCII 字符，字符集为字母、数字、点、下划线和连字符，区分大小写。单个空值、重复头、逗号合并值和非法字符均为 400/4001。缺省时走原有写入。

| 情形 | 结果 |
| --- | --- |
| 编号首次成功 | 200，原 JSON envelope，`Idempotency-Replayed: false`。 |
| 同一精确 app/env、编号、意图 | 200，首次成功的业务 `data`，`Idempotency-Replayed: true`。版本、时间和值等来自回执。 |
| 同一 app/env 与编号，业务意图不同 | 409/4091。编号跨四类操作共享，冲突时原回执保持。 |
| 本次写权限不足 | 原 403/4031。授权通过后才会读取或占用编号。 |
| 并发占位还在处理，当前查不到已提交回执 | 409/4091 并提示用相同编号和原意图再试。 |
| 第一次写入失败 | 原错误语义。事务回滚，编号可重新尝试。 |
| 已存回执损坏或版本不支持 | 500/5000，停止重放。 |

每次请求使用自己的 `X-Trace-Id`。编号对应某次保存，当前值可能已经更新，查当前状态继续使用原 GET。相同 scope 内另一把当前有效的 key 可重放，撤销的 key 返回 403。权限仍以精确 app/env 为单位。回执仅包含成功响应的业务数据及请求摘要，不保存 API key 或原 trace。

## 请求意图与结果版本

意图编码 v1 先写 16 位大端版本，再依次编码操作名、app、env、对象名称和下表字段。每个值带类型标记。字符串由 32 位大端长度与原 UTF-16 代码单元表示，列表带 32 位元素数并逐项编码，数值按 DTO 的 32/64 位类型大端编码，布尔为一字节。null 有独立标记。将这些字节做 SHA-256。固定向量由测试维护。后续增加编码版本时须保留已存回执的重放能力。

| 操作 | 对象名称之后的字段顺序 |
| --- | --- |
| 配置保存 | value、description、expectedVersion、operator、reason |
| 配置回滚 | targetVersion、operator、reason |
| 旗标保存 | enabled、rolloutPercentage、allowlist、expectedVersion、operator、reason |
| 旗标回滚 | targetVersion、operator、reason |

按现有 DTO 解析和验证后的值计算意图。属性顺序和排版可变。缺省与显式 null 在 DTO 相同的情况下等效。空串、空列表、列表中的顺序和重复项、Unicode 表示、operator 和 reason 都参与比较。精确代码单元避免在字符编码替换时混淆请求。HTTP trace、凭证和地址与业务摘要独立。

结果编码 v1 存放 ASCII 转义的 JSON data 与完整 Instant 表示。重放验证版本、字段结构与对象归属，再恢复原响应类型，因此数据库当前行的时间精度和后来写入均不影响重放。表里使用 `TEXT`，应用上限 60,000 个 ASCII 字节。[最大字段及合成样本测量](CURRENT_STATE.md)

## 同事务提交与保留

V5 追加 `write_receipt`。MySQL 用 `utf8mb4_0900_bin` 比较 app/env，用 `VARBINARY(128)` 比较编号。复合唯一索引保护这三个字段，H2 使用 JPA 创建对应表。应用先查已提交的回执，未找到时直接 INSERT 占位。当前行、历史、配置 revision 和成功回执在一个事务中提交，占位对其它事务不可读。Watch 仍由提交后通知。

只处理回执 INSERT 的唯一约束或占位锁超时。失败事务退出以后，用新事务读取已提交回执。匹配时返回旧结果，未查到时提示调用方再试。业务表的唯一约束和版本冲突走原处理。回执 SQL 设置 5 秒 JDBC 语句超时，数据库自身锁等待限制也可能先到。事务中发生失败会一起回滚。应用只在有原授权的请求下尝试一次业务写入。

成功回执持续保留。每笔成功带编号的写入增加回执数据和索引负担，备份和恢复应把六张表与 Flyway 元数据置于同一一致区间。保护回执与业务历史的权限和缓存边界相同。对于已提交且保留的同一 scope/编号/意图，业务效果只提交一次。H2 内存重启、恢复到缺少回执的备份、手工清理与旧服务绕过协议都会影响这个保证。

V5 只增加回执表，现有业务行、列、索引及 V1–V4 迁移身份保持。切换前暂停旧写入者，准备同一库的完整恢复副本。旧服务会忽略编号。故障时按 Flyway 历史和实际结构决定恢复步骤，恢复目标使用隔离库。[V5 切换和实包复现](RUNBOOK.md#config-plan07-幂等写入与回执)
