# config-center 审查与升级提案

2026-11-23 · 待用户确认。以 `0258b9c` 和接管改动为审查基线。这里记录代码审查、已复核行为和可选择的下一阶段。正式范围以用户选定的目标与验收为准。

## 首选路线

先把 **可靠变更** 做成能复现和讲清的 Java 工程案例，再让一个已有应用消费真实开关。服务端继续独立运行，ACGN History Analyzer 可以承接用户可见的效果，RunProof 可以承接对关键变更的受控验证。如果投递偏前后端联动的岗位，再做一页配置发布工作台。单独做全套后台的价值取决于是否有操作员真正需要的发布流程。

现有后端已经能演示配置创建、并发版本冲突、追加历史、回滚、ETag、Watch 以及 Feature Flag。主要展示缺口是稳定的产品场景和外部读回证据。H2 的临时性仍适合开箱演示，MySQL 可以提供跨进程重启的持久验证。用合成业务数据、固定运行手册和备选录屏让演示可重复，持续价值来自一个真实消费者及其反馈。

## 仓库审查

覆盖服务端控制器、请求校验、错误映射、两类写入与历史、Watch 通知及指标、JPA 和 V1/V2，客户端入口、HTTP/重试/断路器/缓存，以及 Maven、CI、Docker/Compose 和已有文档。实际运行结果见 [当前状态](../project/CURRENT_STATE.md)。下表的源码观察用于排优先级，边界试验另列为下一阶段验收。

| 优先级与范围 | 发现与影响 | 待审处理 |
| --- | --- | --- |
| 优先 · CLI 编码 | `DemoRunner` 生成已编码 URL，`ReliableHttp` 使用 RestTemplate 的字符串 URL 重载。实际 CLI 以 `userId=a+b` 请求时，服务端收到 `a%2Bb`，导致白名单判定错误。直接发一次正确编码的 HTTP 请求返回预期的 true。 | 传入已编码 `URI` 或由单层统一编码。用实际 HTTP 发送覆盖普通值、加号、空格、中文和百分号。 |
| 优先 · 回滚原因边界 | 两个 rollback DTO 允许 500 字符，服务把目标版本前缀拼入 `reason`，V1 历史列也是 500。H2 JAR 的配置回滚用 500 字符触发 HTTP 409/code 4091，当前版本和历史都保持为两次写入后的状态。Feature Flag 路径有相同的长度设计，待两类路径的 MySQL 边界实测。 | 确认兼容策略后，优先考虑单独保存回滚目标版本并保留原文与现有表示的兼容层。若选择调整允许长度，应明确输入与旧客户端的影响。两类回滚都验证当前行和历史在失败时无部分提交。 |
| 优先 · 更新保护与写入归因 | `expectedVersion` 仅在已有行时校验且可省略，rollback 无对应当前版本前置条件。`operator` 来自请求体，可用于备注；写入权限由 API key 和命名空间匹配决定。 | 约定 create-only、版本条件、旧调用兼容和认证操作者。若引入幂等请求，定义重放、同键不同输入、保留期及错误码。 |
| 优先 · Watch 与一致性 | `ConfigService`、revision service、条带锁、notifier 和 controller 共同保障事务及提交后唤醒。JVM 注册键按字符串精确匹配，V1 使用 `utf8mb4_unicode_ci`，大小写别名的数据库身份与等待键可能不一致。当前进程内条带锁在 revision 更新路径持续到事务完成。 | 先在 MySQL 测别名、并行首次创建和注册竞态，用户决定规范化及旧标识处理。记录回滚事务、拒绝、超时、断连后的等待资源。需要多实例时再设计跨进程事件与恢复。 |
| 优先 · Watch 客户端新鲜度 | `watchOnce` 在通知后调用 fetch，瞬时故障时可能返回有效但陈旧的缓存。`DemoRunner` 仍更新本地 cursor，下一次变更前可能缺少新鲜快照。源码观察。 | 区分已观察 revision 和已应用快照，明确陈旧态与重新同步条件。补断网后恢复和 H2 重启游标回退的测试，保留旧客户端兼容约定。 |
| 中 · 条件 HTTP | 列表与 ETag 来自同一排序快照。JAR 实测同标签、弱比较和标签列表均返回 304。对有表示的列表，`If-None-Match: *` 返回 200。每次条件读当前仍要查表、读全量并计算 hash。 | 补通配符的协议测试，核对控制器和 Spring MVC 各自负责的条件判断。测到查询压力后再选快照缓存，保证数据库重置和多字段变化不会误回 304。 [RFC 9110 §13.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2) |

| 中 · Feature Flag 模型 | 已有总开关、allowlist、稳定分桶与解释。分桶兼容依赖现有 `userId + ":" + featureName` 输入和 SHA-256 截取。旗标变化与配置 Watch 有不同语义。 | 增加黄金分桶向量和身份规范，改算法时版本化。需要客户端实时获取旗标时单独设计读取/订阅，先验证实际消费者。 |
| 中 · 数据、Compose 和权限 | 主库与测试库分离，持久 schema 版本化。读 API、Actuator 细节与本地 key 使用现行 loopback 范围。CI 覆盖空库应用 V1/V2 及后续无迁移启动。下一次变更仍需旧库升级、恢复和回滚方案。 | 用非 root 测试账号和合成样本验证空库、旧库和保卷重启。若将服务开放给其他用户，先选读取权限、管理认证、密钥轮换、审计身份和展示数据边界。 |
| 中 · 限流、trace 与运维可解释性 | `RateLimitInterceptor` 用来源、方法和路径模式取有界 LRU 桶，Watch 压力有等待与拒绝指标。请求 trace 可以在 HTTP 和日志中关联。进程重启会清空限流和等待状态。 | 测桶与等待队列在并发下的上界，区分普通 429 和 Watch 容量拒绝的指标。以低基数标签观测写入冲突、超时、延迟和缓存结果。跨代理部署时先决定可信来源和 trace 取值边界。 |
| 中 · 可交付证据 | 现有 CI 分开运行快测和 MySQL。CLI 是 Maven 启动的演示项目。POM 仍用 `1.0.0`，历史标签则指向更早的源码。 | 固定候选构建身份，输出可复查的小场景和一条启动路径。所需交付形式以及版本/标签由用户决定。 |

## 候选阶段与验证

### 1. 可靠性和后端结构

同一个变更在正常、竞争、超时、失败重试或回滚场景下，都应能通过当前状态和历史解释结果。

- 兼容基线先锁定当前 API、错误 envelope、排序、分桶、历史版本、revision 和 cache 行为。先修复已经复现的 CLI 编码，梳理回滚原因约束、Watch 跟进失败及 MySQL 命名空间身份。
- 分批向模块化单体演进。可以按 `config`、`flags`、`watch` 和共享 HTTP/诊断能力调整包组织。Controller 处理协议和校验，应用服务拥有用例事务，纯 Java 部分承载可单测决策，JPA 模型及仓储负责表和锁语义。先挑一条调用链穿透验证，再移动可重复的其它组件。
- 如果首个产品目标需要发布动作，建议以单命名空间的一次可靠提交为原型，明确当前版本校验、回滚、新旧客户端并存、重复请求和结果不确定的读回策略。幂等记录若最终采用，应与业务效果在同事务内持久化，且绑定操作类型、命名空间、请求意图和唯一键。先证明数据边界，再考虑跨进程投递或专用消息系统。
- 使用 H2 维持快速回归。使用隔离 MySQL 驱动同一 key 的竞争、同 namespace 不同 key 首次写入、失败事务历史不增长、旧库迁移与重启。并发测试用可控屏障；故障演示保存实际请求结果、读回、历史和相关 trace。
- 验收证据包括命令、源码 SHA、JDK/MySQL 版本和数据集范围。性能可报告相同数据量、并发和预热下的 p50/p95、错误率、查询次数、304 比例及 Watch 等待峰值。采到实测基线后再定目标。

### 2. 一个真实 Java 消费者

优先考虑 ACGN History Analyzer 的年度报告功能。它已有 Java 后端、React 界面及 Mock 分析说明，可以用合成数据做端到端回放。建议由其服务端在处理分析前评估 `analysis.annual-insights`，用专用 app/env 和稳定的演示用户标识。关闭时界面与后台行为一致，开启时固定一批用户得到 Mock 结果，配置服务不可达时执行已决定的默认策略。前端展示功能状态和可恢复提示，业务端保有最终的执行控制。 [Analyzer 项目说明](https://github.com/MyKr-YSteinsK/ACGN-History-Analyzer/tree/e9c8c2656e934fd1d0ccbe7ce694586483d97f42)

建议先经现有 HTTP API 做薄适配。稳定消费方出现后，再评估是否提取 Java SDK 或提供 OpenFeature Provider。后者适合明确默认值、评估上下文和评估详情，需先验证现有语义映射与失败行为。 [OpenFeature 评估规范](https://openfeature.dev/specification/sections/flag-evaluation/)

验收可以用一个固定账号集合展示同输入分桶稳定、白名单覆盖、版本回滚、依赖断开与恢复。记录实际接口、消费端行为、合成数据和执行提交。若后续使用真实应用，另行核对隐私、登录身份、模型花费和数据流；测试用例无需调用外部模型。

另外两个应用适合验证不同的接入方式。

- **ACGN Works Tracker** 已有 Servlet、JDBC、MySQL 及 jQuery 界面。可用一个统计视图开关展示传统 Java Web 的渐进接入。优点是应用场景明确，投入主要在接口适配和旧栈运行。 [作品管理仓库](https://github.com/MyKr-YSteinsK/ACGN-Works-Tracker/tree/15284985dd8b16f9f848ade945a29eb8134e6350)
- **Bangumi Side B** 已有 SQLite 数据和静态/PWA 发布链路。更适合在构建阶段消费配置快照，验证版本可追溯和离线可用。它的线上页面继续保持静态，候选设计应评估能否让可追溯性超过多一个服务的成本。 [Bangumi Side B 说明](https://github.com/MyKr-YSteinsK/bangumi-side-b/tree/b6c21de22be97e3c731452fa470668ed4be9c56d)

### 3. RunProof 作为独立的验证案例

RunProof 的 RPF-51 已有受控的 loopback HTTP adapter，能读取当前值和历史、比较创建/更新、校验过时版本冲突或未授权请求。其后续配置目标合同固定了 `config-center` 基线 `0258b9c`，live 合同还固定旧 JAR SHA-256。接管后构建属于新候选，必须独立复核，保留历史合同和原有证据。 [旧受控 HTTP 适配器](https://github.com/MyKr-YSteinsK/runproof/blob/b076d2c4206683ba96eb8ffc6ae2cd290074af0c/runtime/runproof_runtime/effectwitness/config_http_adapter.py) · [旧构建合同](https://github.com/MyKr-YSteinsK/runproof/blob/b076d2c4206683ba96eb8ffc6ae2cd290074af0c/runtime/runproof_runtime/effectwitness/config_live_contracts.py)

有实际采用价值的下一步是为一个新配置变更候选做 **提交后响应丢失** 的受控例子。用固定合成 key、限定写入、独立读回当前值和历史检验结果。观察到提交时停止重试并归档新版本，观察与预期冲突时停止写入并记录证据。第一版使用确定性驱动和本机隔离环境，保留双方提交、目标 JAR 标识、请求轨迹、预期效果和实际读回。读回与写入若使用同一个后端，证据仍处于同一数据库/服务信任域。

两个仓库继续各自提供独立运行方式。可共享的是 HTTP 契约、合成场景与证据格式。跨仓库改动、更新既有 pin、外部 Provider 或发行物是独立授权。面试时用这一条真实工程案例同时解释 config-center 的事务边界和 RunProof 的验证职责。

### 4. 最小发布工作台

作为可选界面扩展，首个用户流程聚焦在 **选择 app/env → 比较提议值和当前版本 → 提交 → 查看历史/回滚 → 观察生效**。包含加载、空历史、明确的 409、过期编辑和提交结果未知。增加少量只读指标，避免把 Actuator 原始输出直接当管理界面。

若只做合成数据本地演示，可以优先比较 Spring 同源静态页与一个轻量 React/TypeScript 工作台。面向实际用户时，先确定管理端会话或 BFF、写授权、配置值遮盖与审计。API key 存在服务端边界，浏览器只用对应的最小会话。验证桌面键盘与窄屏操作、应用/环境切换状态、冲突后的重试和 UI 与 API 状态一致。发布前单独批准数据和网络范围。若 ACGN 业务界面已足够呈现发布效果，可以保留控制台为后续候选。
